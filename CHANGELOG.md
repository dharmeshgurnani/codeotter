# Changelog

## Unreleased

- **Review result as a GitHub check run.** Where the GitHub App is installed on the repository, `codeotter/checks` is a check run instead of a commit status: in progress while the review runs, then completed with a conclusion (failure when a blocking custom check failed, neutral for "changes requested" or any other failed gate or check, success otherwise), a summary of scores, blast radius and gates, and an annotation per finding with a file and line (sent 50 per request, the Checks API limit). A failed review completes the run as failure with the model's error. Without the App on the repository, and on every other git server, the `codeotter/checks` commit status stays as before (only when custom checks ran); one commit never gets both. The App manifest now asks for `checks: write` and `members: read`; an existing App without `checks: write` keeps getting the status until the permission is granted.
- **Override failing checks.** `/override <check name|all> <reason>` in a PR comment overrides failing custom pre-merge checks when the repository's new **Check overrides** setting is on (Repository settings, default off). Only a requested reviewer may override (a user, or a member of a requested team on GitHub and Gitea/Forgejo; individual reviewers on Bitbucket Cloud/Data Center, Azure DevOps and GitLab), never the pull request's author. Overrides are stored with the review for the head commit they were given on (a review of a later commit starts without them), shown on the review page, written to the audit log (`check.override`, refusals as `check.override.refused`), and `codeotter/checks` is republished with them.
- **Review next.** Home opens with a ranked table of the active organization's open pull requests (every forge, developer-scoped), also served as `GET /api/review-next?org=`. The priority is plain arithmetic over stored model output and the PR itself: 0.4 × correctness risk + 0.2 × blast radius (the newer of fast triage and the last review), 12 per failed block gate and 8 per failed warn gate (3 counted each), +10 changes requested / −10 approved, 6 per day waiting since the last update (at most 30), +15 overdue, +5 for 50 changed lines or fewer, −5 above 1,000, −40 for drafts; the Priority cell's tooltip lists the terms. A PR with no triage or review shows *unscored* and ranks by waiting time; scores from an older commit carry `*`. Related PRs share a Group (same linked issue or Jira/Linear ticket, a base that is another open PR's head, or a branch prefix such as `feat/auth-1`, `feat/auth-2`) and sit together. Settings → Workspace → **Review queue** sets a review SLA in hours per organization (settings key `reviewSla`); older open non-draft PRs show *overdue*. Open-PR rows now carry `createdAt` on every forge, and the GitHub list adds `body`, `createdAt` and `headRefName`.
- **Learned rules.** CodeOtter reads signal on its own inline comments: thumbs up/down and equivalents (👍 ❤️ 🎉 🚀 up, 👎 😕 down) on GitHub, GitLab (award emoji) and Forgejo/Gitea (reactions; Bitbucket and Azure DevOps have none to read), replies the language model reads as "intentional / false positive" (and `@codeotter remember`), findings a later push fixed, findings dismissed on the review page, and findings still open when the pull request closed (ignored). It is read through the PR queue after an auto re-review and when a pull request closes (GitHub and Forgejo/Gitea close webhooks, the catch-up poll elsewhere); there is no new poll. When two or more similar findings are pushed back on, the language model drafts one team rule from them and the replies; it is stored as **suggested** and nothing is suggested when the model fails or answers no rule. Repository settings has a **Learnings** table (Rule · Status · Fixed · Ignored · Dismissed · 👍 / 👎; status active, off, locked or suggested) with Accept, Reject/Remove, Lock/Unlock and Switch off/on row actions, and new settings: **Auto-promote suggested rules** (off by default: suggest only) after **Promote after** findings, and rule health: a learning whose findings are fixed less than **Switch off below** (20% by default; Never) of at least **Rule health sample** (5) closed findings switches off unless locked. The language model now marks which numbered learning a finding enforces, which is how findings are tied to rules. Automatic switches are audited as `rule.auto-off` / `rule.auto-on` (actor `auto`), row actions as `rule.update`. Stored per repository in the setting `learned:<repo>` (the newest 80 findings), cleared when the repository is removed. Settings row actions now receive the page's `?org=` / `?repo=` scope.
- **Sandbox run.** Repository settings gain a **Sandbox run** section (admins and owners; off by default; shown disabled when `docker version` gets no answer from a daemon): image, setup command, setup network, test command, test targets and a time limit (1 to 30 min). When on, a review fetches the PR head on the host (refs/pull/<n>/head or the provider's equivalent, over HTTPS, the token only in git's environment, redirects refused, the fetched commit must be the reviewed SHA) and runs setup then test with `docker run --rm --network none --read-only --cap-drop ALL --security-opt no-new-privileges`, a non-root user, 2 CPUs, 2 GB memory, 256 processes and no host environment; only setup can get network, and only when the admin turns it on. Commands come only from Repository settings, never from the model, the PR or `.codeotter.json`; the language model (else System One, a yes/no per target) picks which listed test targets to pass, and picks outside the list are dropped. Pass/fail, exit code, failed tests (TAP, Jest/Vitest, pytest, go, cargo) and the output tail go to both engines as untrusted evidence and to a Sandbox run section on the review page; a run that cannot start shows its error. A time-out or cancel removes the container and the temp tree. Stored as `repoSettings[repo].sandbox` (`core/sandbox.ts`); git adapters gain `fetchSource()`.
- **Context from related repositories.** Repository settings has **Related repositories**: up to 7 other onboarded repositories in the same organization and on the same provider (a save naming any other repository is refused; stored as `repoSettings[repo].review.related`). A review searches them for usages of the symbols the pull request exports (all changed symbols when none is exported) through the provider's code search: GitHub code search through `gh`, GitLab blob search, Bitbucket Cloud workspace code search; Forgejo, Gitea, Bitbucket Data Center and Azure DevOps have no code search on the configured origin and show as "No code search". Bounded to 5 symbols, 6 usages per repository and 24 in total, 8 s per repository and 20 s overall; results are cached for 30 minutes by related repository and reviewed head SHA, and a repository that fails or times out is reported without failing the review. Usages join the language model prompt (at most a tenth of a local model's `contextChars`), the System One state, the blast radius score and the Mermaid diagram as outside-repository nodes labelled with their repository; the review page lists them under Blast radius details. A developer sees usages only from repositories assigned to them and a count for the rest; posted PR comments carry totals only, no repository names or code. Forge adapters gain `searchCode`.
- **Rules from the head branch.** Repository settings add **Rules source**: Base branch (the default) or Head branch. With Head branch, a same-repository pull request is reviewed with the AGENTS.md, CLAUDE.md and `.codeotter.json` of its head commit (read by SHA, cached per commit), so a rule change can be tried on a branch before it merges. Only guidance is taken from the head: its copy of a guide replaces the base's (a guide it deletes is still read from the base), its path instructions are added to the base's, and its checks with a new name and mode warn or block are added. Everything that loosens a review stays the base's: skip rules, `reviewDrafts`, `pathInclude`, `pathExclude`, and every existing check (a head entry that switches one off, softens it or rewords it is ignored). Fork pull requests always use the base and the fork is never read. When the head's rule files differ, the review page shows a **rules from head** badge with the commit and files (the ignored keys on hover) and the posted review summary names them. **Changed:** in the default Base branch mode, AGENTS.md and CLAUDE.md are now read from the base branch too; before, reviews read them from the PR head (on Forgejo/Gitea, from a fork's head repository). GitHub PR reads add `isCrossRepository` to tell forks apart.
- **`/fix stacked`.** A comment command, and **Open fix PR** on the review page (review access to the repository), that commits the stored review's suggested changes (open findings that carry a model-written suggestion; nothing else) on a branch `codeotter/fix-<pr>-<shortsha>` made from the PR's head commit, and opens a pull request into the PR's head branch that links back and lists the findings it fixes. Each suggestion is located in the head by its reviewed lines and their context; one that no longer applies, is already in or overlaps another is skipped and listed. The original PR gets a comment with the link. Re-running updates the open fix pull request (GitHub, GitLab and Azure DevOps move its branch to a fresh commit on the head; Forgejo and Gitea add a commit to it). Same-repository PRs only: a fork PR is refused with a comment saying why. GitHub (as the App bot when installed), GitLab, Forgejo, Gitea and Azure DevOps; Bitbucket Cloud and Data Center are refused (their commit APIs take multipart uploads). Recorded in the audit log as `fix.stacked`.

## 0.9.0 (2026-11-20)

- **Review profile and minimum severity.** Repository settings add **Profile** (Chill: high and medium findings only, 5 findings, self-check at 7; Balanced: unchanged, the default; Assertive: nitpicks included, 12 findings, self-check at 3) and **Minimum severity to post** (Nit / Low / Medium / High). The profile sets the default Max findings and Self-check and the model's instructions; a Max findings or Self-check value moved off the profile's default is kept as set. The posted review summary and inline suggestions carry only findings at or above the minimum severity; the review page shows all of them.
- **Path filters, path instructions and skip rules.** Repository settings gain include/exclude path globs (`*`, `?`, `**`; excluded files never reach a model, and a PR whose every file is excluded fails with that reason), path instructions (`glob: instructions`, added to the language model prompt only when a matching file changed) and auto-review skip rules: review drafts, skip authors (`*` wildcard, e.g. `dependabot[bot]`, `*[bot]`), skip base branches, only base branches, skip title keywords and skip labels (`codeotter:skip` always skips). A `.codeotter.json` at the repository root sets the same keys (`pathInclude`, `pathExclude`, `pathInstructions: [{ path, instructions }]`, `reviewDrafts`, `skipAuthors`, `skipBaseBranches`, `onlyBaseBranches`, `skipTitleKeywords`, `skipLabels`; schema in `core/repo-rules.ts`); each key it sets wins over Repository settings, which shows when the file is in effect. The file is read from the base repository at the PR's base branch, never from the head, so a pull request (fork or not) cannot loosen its own rules. The GitHub poll now lists each PR's base branch. Settings forms gain a `textarea` field (one item per line).
- **Custom pre-merge checks.** Repository settings take a list of checks: a name, a yes/no question (yes passes) and a mode (off, warn, block). System One asks them as extra gates next to the built-in ones (chunked for local runtimes); without System One the language model answers them in its review. Results show with the gates on the review page and in the posted scores and review comments, and set a `codeotter/checks` commit status: failure when a block check fails, success (warnings named) otherwise. Settings forms gain a `rows` field (a table of repeatable rows with sub-fields). Stored as `repoSettings[repo].review.checks`; a `"checks"` array in `.codeotter.json` on the base branch replaces them for that repository.
- **Post as the GitHub App bot.** With a GitHub App and its private key stored (Create app saves both), comments, inline reviews, triage commit statuses, PR description updates and command reactions go out as `<app>[bot]` through an installation access token: an RS256 app JWT is exchanged per repository owner (`GET /repos/{owner}/{repo}/installation`, `POST /app/installations/{id}/access_tokens`) and the token cached until five minutes before it expires. Repositories the app is not installed on, and instances without an app, keep posting as the operator's saved token, `GH_TOKEN` or `gh` login (or the App, on an install with no other GitHub credential). Reads are unchanged. One installation-token cache now serves both bot writes and App-only installs (0.8.2). The GitHub gear under Settings → System → Git providers shows who posts.
- **Replies on inline comments.** With PR comment commands on (Repository settings), a reply from an owner, member or collaborator (write access on Forgejo/Gitea) under a CodeOtter inline comment gets an answer in the same thread from the language model, given the finding, its diff hunk and the conversation. `@codeotter remember <rule>` saves a team learning; when the model reads a reply as "intentional" or "false positive" it offers the matching `remember` line instead of saving it. CodeOtter never answers its own comments or bots, and replies go through the PR queue. GitHub, GitLab (diff discussions; the hunk is cut from the merge request's diff), Forgejo and Gitea for now; Bitbucket and Azure DevOps not yet. Replies and `@codeotter remember` are recorded in the audit log as comment commands. New GitHub Apps subscribe to `pull_request_review_comment` (an existing app: add the event under the app's Permissions & events), `gh webhook forward` forwards it, and new Forgejo/Gitea repository hooks add `pull_request_review`.
- **Resolve fixed comments.** On an incremental re-review, CodeOtter's own inline comments that the push since fixed are resolved: a finding the re-review no longer reports is checked against the delta diff by System One (yes/no) or the language model, and only those judged fixed are touched. GitHub resolves the review thread through GraphQL (or replies when the token may not resolve); Bitbucket Cloud resolves the comment; Bitbucket Data Center resolves the thread (8.9+, else replies); Azure DevOps replies and sets the thread to fixed; GitLab resolves the diff discussion (or replies when the token may not); Forgejo and Gitea, which have no resolve API, get one PR comment listing them. Per repository: **Resolve fixed comments** in Repository settings, on by default, active while inline suggestions are posted.
- **Fix with AI.** Each finding, and the review as a whole, has a self-contained prompt for a coding agent (Claude Code, Codex, Cursor, Copilot agent): repository, PR, branch, `file:line`, the finding, its diff hunk, the suggested fix and the repository's AGENTS.md/CLAUDE.md. The review page has **Copy fix prompt** per finding and **Copy prompt for all**; posted review summaries and inline findings carry it in a collapsed "Prompt for AI agents" block (Repository settings → **Prompt for AI agents**, on by default). New comment command **`/fix`** (or `/fix <n>` for one finding of the posted review): the language model writes a patch for the open findings, each hunk is checked against the PR head in memory, and the ones that apply are posted as committable suggestions. Nothing is pushed to the branch. Inline suggestions now keep the indentation of their first line.
- **Jira and Linear tickets as review context.** A pull request's title, branch and description are scanned for ticket keys: Jira keys of the configured projects, Linear keys of the configured teams and `linear.app` issue links (so `UTF-8` or `SHA-256` never match). Each ticket's title, description and acceptance criteria (Jira: the field named Acceptance Criteria; Linear: the description's Acceptance criteria section) join the linked issues, so they reach the review prompt, the System One `issue_requirements` gate, the PR comment and the review-page badges, shown by key (`ABC-123`). Jira Cloud uses REST v3 with an account email and API token (descriptions converted from ADF); Jira Data Center uses REST v2 with a personal access token. Linear uses its GraphQL API with an API key. Connect them under Settings → System → **Issue trackers** (Provider · Server · Status table, Test per row); tokens are sent only to the configured Jira address and `api.linear.app`, redirects are not followed, and fetched tickets are cached for five minutes.
- **Static analysis evidence.** Repository settings has per-repository switches for gitleaks (secrets), Semgrep (`p/ci` SAST rules) and Trivy (dependency vulnerabilities). Each runs on the head text of the PR's changed files in a temporary tree; only results within 3 lines of an added line are kept (Trivy: a package named on an added line of a changed manifest) and handed to the language model, which confirms or rejects each one. Confirmed results become findings tagged with the analyzer. Secret values are never put in a prompt, comment or stored review: tool output is redacted and known values are scrubbed from the model's reply. A missing, failing or timed-out analyzer is shown under Static analysis on the review page and never fails the review. Settings → System → Analyzers lists availability (PATH or downloaded) and downloads pinned releases on click: gitleaks 8.30.1 and Trivy 0.76.2 archives checked against their SHA-256, Semgrep 1.186.0 into a pip venv.
- **Analytics** (sidebar, under Home; `GET /api/analytics?org=&days=7|30|90`). Every finished review records an event: language-model input/output tokens as Anthropic, OpenAI-compatible and OpenRouter responses report them, estimated cost (the provider's own cost when it sends one, else a per-model price table; local models count as $0; unknown hosted models are counted in tokens only), duration, findings by severity, gate results, inline suggestions posted and suggestions the author applied (accepted fixes). Suggestions posted from the review page and findings dismissed into learnings are recorded too. The report shows totals (reviews, pull requests, findings, acceptance rate, tokens, cost, review time), review volume per day (per week for 90 days), a per-repository table, findings by severity and gate failures, scoped to the active organization; developers see only their assigned repositories. Events are a new PocketBase collection `analytics` (migration `1727400006_analytics.js`), or `analytics.jsonl` with file storage. Reports gain a `bars` section kind (plain SVG).
- **Enterprise SSO.** Settings → System → Auth providers has an **OpenID Connect (SSO)** row: issuer URL (endpoints and keys read from its `/.well-known/openid-configuration`), client ID and secret, display name (the sign-in button's label) and **Allowed email domains**. It uses PocketBase's `oidc2` provider, so Forgejo keeps `oidc`. SSO invites match a verified email (PocketBase's and the IdP's `email_verified`) in an allowed domain; without allowed domains, no SSO email matches. **Auto-admit** (off by default) lets users of those domains in as developers with no repositories. **Require SSO** hides and refuses the other sign-in providers; an owner signs in another way with `PR_SCORER_RECOVERY=1`. The issuer cannot change while accounts are linked to it, and an account that also signs in another way is reached through SSO only with an allowed-domain email.
- **Audit log.** An append-only record of sign-ins (and refusals), account role and repository-access changes, invites, settings saves (the page and the fields sent; passwords, tokens, keys and secrets stored as `••••`), model, git and auth provider changes, webhook secrets, repositories onboarded or removed, reviews posted to pull requests (by account, comment author or `auto`), comment commands (including `/fix` and replies under inline comments), Issue trackers saves, analyzer downloads and deletes, and local model downloads, switches and deletes. Owners read it under Settings → Workspace → Audit log, filtered by action and actor and scoped to the active organization, and download it as CSV (`GET /api/audit/export`). The newest 10,000 entries within 180 days are kept (`CODEOTTER_AUDIT_MAX`, `CODEOTTER_AUDIT_DAYS`). Stored in a new PocketBase `audit` collection (migration `1727400007_audit.js`), or `audit.jsonl` with file storage.
- **GitLab.** gitlab.com or one self-managed origin (`gitlab~group[/subgroup...]/project`, organization scope `gitlab~group`): merge request reviews, inline suggestions (`suggestion:-N+0` for multi-line fixes), commit statuses, PR tools, linked issues, comment commands (trusted for Developer access or higher), auto-review, the `codeotter/checks` status, replies in diff discussions and resolving fixed discussions. Connect it under Settings → System → Git providers or with `GITLAB_URL`/`GITLAB_TOKEN`; onboarding a project registers a project hook (merge request and note events) at `/webhooks/gitlab`, checked by its `X-Gitlab-Token` in constant time and de-duplicated by `Idempotency-Key` (or `X-Gitlab-Event-UUID`). Sign-in adds **GitLab** through PocketBase's `gitlab` OAuth2 provider; invites match by username.

## 0.8.3 (2026-11-20)

- **Version in the sidebar.** The running release (`v0.8.3`) sits next to the logo.
- **Posting and automation on by default.** *Post scores on PR*, *Add PR review as a comment*, *Post inline suggestions*, *Auto-review* and *PR comment commands* now start on; turn them off per repository in Repository settings. Repositories with saved review settings keep them.

## 0.8.2 (2026-11-17)

- **GitHub works with only the GitHub App.** An install whose only GitHub credential is the App made in onboarding (no saved token, no `GH_TOKEN`, no `gh auth login`; Railway, Render, Docker) now lists, reviews and comments on pull requests as the App, using an installation token for the repository's owner. Before, every GitHub call failed silently and open pull requests never appeared. A saved token, `GH_TOKEN` or a `gh` login still takes precedence.
- **PocketBase sign-in renews after the token expires.** A long-running server (Railway, Render, Docker) showed `Storage 403: Only superusers can perform this action.` once its superuser token expired: PocketBase answers 403, not 401, to an expired token on record endpoints, so the server never signed in again. It now re-authenticates on 401 and 403.

## 0.8.1 (2026-11-10)

- **Container start without `PB_ADMIN_EMAIL`** (Render, Railway): `bin/start.sh` now exports its PocketBase admin defaults, so the server signs in with the superuser it just created instead of failing with `PocketBase auth 400`.
- **No default repository outside a checkout.** Without `REPO`, a `gh` login or a git remote (Docker, Render, Railway), a new install starts with no onboarded repositories, so onboarding opens, instead of falling back to `dharmeshgurnani/CodeOtter`.
- **GitHub App manifest**: *Create app* no longer lists `installation_repositories` as a default event, which GitHub rejected ("Default events unsupported"). Apps receive it without subscribing.
- **GitHub App install returns to onboarding.** New apps no longer request user authorization during installation, so GitHub sends the installer to onboarding. Apps already created that way land on the sign-in callback with an `installation_id`; that now goes back to onboarding (or Git providers) instead of failing with "Sign-in state mismatch" on the login page.

## 0.8.0 (2026-11-08)

- **GitHub Action** ([codeotter-action](https://github.com/dharmeshgurnani/codeotter-action), for GitHub Marketplace): a workflow on `pull_request_target` / `issue_comment` posts its own event payload to `/webhooks/github`, signed with the instance's **Action secret** (new, under Settings → System → Git providers → GitHub; repository secret `CODEOTTER_SECRET`). The server URL comes from `url:` in `codeotter.yml` on the default branch. No App install and no relay. Re-creating the GitHub App with *Create app* now keeps the forwarder and Action secrets.
- **TypeScript.** `core/`, `tui/`, `bin/`, `test/` and `web/scripts/` are strict TypeScript (`.ts`), run directly by Node's type stripping, with no build step. Node 22.18 or later is required. `pnpm start` runs `node core/server.ts`, and `codeotter` is `tui/codeotter.ts`. `pnpm typecheck` (strict, no `any`) runs in CI and before `pnpm test`. Malformed API request fields are treated as empty instead of failing with a TypeError. PocketBase migrations stay JavaScript.

## 0.7.0 (2026-11-08)

- **HTTP on Hono.** The backend's 32-branch request handler is now a Hono app (`core/app.mjs`) with one route module per area under `core/routes/`; access checks are route middleware, errors go through one `onError`, built assets through `serveStatic` (streamed, with `Last-Modified` and range requests). Responses are unchanged, except: unknown `/api/*` paths and wrong methods on API routes answer a JSON 404 instead of the web app; API bodies over 1 MB (webhooks 2 MB) answer 413 instead of 500. `hono` and `@hono/node-server` are the backend's only dependencies.
- **Backend split into modules.** `core/server.mjs` (5,500 lines) is now the entry point and HTTP routes; the rest moved verbatim into one module per subsystem under `core/` (config, providers, local models, store, git, models, diff, context, engines, review, comments, PR tools, queue, views, settings pages, access). No behaviour change; `node core/server.mjs` and the TUI imports are unchanged.
- **Bitbucket and Azure DevOps.** Bitbucket Cloud (`bitbucket~workspace/repo`), Bitbucket Data Center (`bitbucketdc~PROJECT/repo`) and Azure DevOps Services (`azure~org/project/repo`) repositories work like Forgejo and Gitea: reviews, inline suggestions, scores and triage statuses, PR tools, comment commands and auto-review. Connect them under Settings → System → Git providers (Bitbucket: API token with the Atlassian account email, or an access token; Data Center: server URL and HTTP access token; Azure DevOps: organizations and a personal access token), or with `BITBUCKET_TOKEN`/`BITBUCKET_USER`, `BITBUCKET_DC_URL`/`BITBUCKET_DC_TOKEN`, `AZURE_DEVOPS_TOKEN`/`AZURE_DEVOPS_ORGS`. Onboarding a repository registers a webhook (Azure DevOps: three service hook subscriptions) at `/webhooks/bitbucket|bitbucketdc|azure`; Bitbucket deliveries are HMAC-checked, Azure DevOps ones carry the secret in an `X-CodeOtter-Secret` header (Azure cannot sign). Sign-in adds **Bitbucket** and **Microsoft** (Entra ID, pinned to one tenant; Microsoft invites match by email). Azure DevOps has no diff endpoint: the diff is built from the changed files' blobs. Comment commands are trusted for write access (Bitbucket: needs an admin token to read permissions; Data Center: direct user grants), and on Azure DevOps for private projects only. Provider code moved to `core/forges.mjs`, one adapter per API family.
- **OpenAI-compatible endpoints**: requests for Claude 4 and later model ids now carry `max_tokens: 16000`, and Claude 5 ids no longer carry `temperature`. Claude 3.x and every other model id send the request they sent before.
- **Sponsors**: README Sponsors section; `FUNDING.yml` links it alongside GitHub Sponsors. Added `CODE_OF_CONDUCT.md` (Contributor Covenant 2.1), a pull request template and a weekly OpenSSF Scorecard workflow.
- **Webhooks** (`POST /webhooks/github|forgejo|gitea`): new GitHub Apps made by *Create app* carry a webhook for `pull_request`, `issue_comment` and `installation_repositories`; onboarding a Forgejo/Gitea repository registers a repository hook and removing it deletes the hook. Deliveries are HMAC-SHA256 checked, de-duplicated by id and answered before work starts. The GitHub row's gear under Settings → System → Git providers shows the webhook URL and last delivery and takes a secret for a GitHub App created earlier; the Forgejo and Gitea gears show theirs. After a restart, failed `pull_request` deliveries are requested again from GitHub.
- **One review queue.** The poll, webhooks and the forwarder all enqueue pull requests; reviews run one at a time outside the poll, so a long review no longer delays other repositories. A failed auto-review is retried three times, ten minutes apart, with the error kept (`autoReviewFailed`), instead of every two minutes forever. The poll lists up to 200 open PRs per repository (was 30), logs listing errors instead of treating them as "no pull requests", and backs off to every fifteen minutes for a forge with deliveries in the last ten minutes.
- **Forward webhooks here** (GitHub gear under Git providers): runs `gh webhook forward` per onboarded GitHub repository so a localhost instance receives events; status shown per repository.
- Renamed the remaining `pr-scorer` / `PR Scorer` names to Code Otter: browser storage keys (`code-otter.org`, `code-otter.back`, `code-otter.onboarding_done`; the remembered organization and onboarding flag reset once), the `DESIGN.md` and `AGENTS.md` names, and the example `APP_URL`. The `PR_SCORER_*` environment variables are unchanged.
- **Docs moved to [docs.codeotter.io](https://docs.codeotter.io/docs)** (Fumadocs, source in [codeotter-docs](https://github.com/dharmeshgurnani/codeotter-docs)). The README keeps the overview and links to the guides; `docs/ci-triage.md` is now [Fast triage in CI](https://docs.codeotter.io/docs/ci-triage). The header Documentation icon, the sign-in page and the home report link to the docs site instead of the README.
- **One table, one badge.** Every table (settings, home report, review and pull request lists, review-page checks, the loading skeleton) draws through `web/src/components/data-table.tsx`, and every status, count or tag is its `Badge` (4px corners, light tinted fill, neutral-700 text and 1px border). Local models and Manage accounts are tables; Model provider is a Review engines table with Fast triage in the System One dialog; Local models shows each model's runtime (ggmlc, llama.cpp, Python) and the device it runs on. Row actions take icons, icon-only and danger styles, show a spinner while the server works, and stay visible but disabled when they do not apply. Settings pages use the full width; tooltips break into one line per fact; sliders follow the mouse wheel; checkboxes are switches.
- Reviews list: verdict, author and effort columns, newest first, the title as the one link, scores as x/100, and an icon that opens the pull request on its forge; the repository badge only shows on mixed lists.

- **Accepted fixes**: on a re-review after new commits, each earlier suggestion whose code is now in the file but was not at the previously reviewed commit (compared line by line, ignoring indentation) is recorded for the repository. The 10 most recent go into language model and hosted System One reviews as fixes this team accepted; the list (up to 30) is editable under Settings → Repositories → ⚙️ → Accepted fixes. The positive counterpart of dismiss-and-remember learnings.

- **PR comment commands**: a pull request comment whose first line is `/review`, `/describe`, `/improve`, `/ask <question>`, `/docs` or `/changelog` runs that action and replies on the PR (`/review` re-reviews and posts scores and review; tools post their result). Only owners, members and collaborators (GitHub `author_association`; Forgejo/Gitea write permission) can trigger one. Polled every minute per onboarded repository; the command gets an 👀 reaction, and failures are replied to. Off by default: Admin → Model provider → Review → PR comment commands.

- **Docs** (Tools card): doc comments (JSDoc, docstrings, Go/Rust doc comments…) for functions and classes the PR adds or changes without one, matching the file's style, as committable inline suggestions.
- **Changelog** (Tools card): a changelog entry in the format, tense and detail of the repository's `CHANGELOG.md`, `CHANGES.md` or `HISTORY.md` at the PR head, shown as a block to paste or post as a comment. CodeOtter does not commit to the PR branch.
- Fixed: the Tools card's apply button (Update PR description, Post inline suggestions) never appeared.

- **Improve** (Tools card): code suggestions only, no scores. Each replaces a line range of the new file and carries a label (possible issue, security, performance, error handling, maintainability, enhancement); the self-check scores and filters them; Post inline suggestions publishes them as committable suggestions.
- Inline suggestions can span several lines: GitHub gets a multi-line suggestion (`start_line`); Forgejo and Gitea, whose review comments cover one line, show the replacement as a code block instead of a committable suggestion.

- **Ask** (Tools card): answers a free-form question about the PR from its diff and guidelines. Answers posted to the PR have HTML comments removed (so they cannot forge CodeOtter's comment markers) and @mentions defused.

- **Tools card** on the review page, driven by `PR_TOOLS` in `server.mjs` (`GET`/`POST /api/tools`): pick a tool, run it, post the result as an upserted PR comment, or apply it. Tools use the language model with the same dynamic context, diff budget and repository guidelines as reviews.
- **Describe**: title, type (Bug fix, Feature, Refactor…), summary bullets and a per-file change table. Update PR description writes a `<!-- codeotter:describe -->` block into the PR body, keeping the author's text and replacing the block on later runs.

- **Self-check**: language model findings go through a second pass of the same model, which scores each one 0-10 against the diff (wrong or unsupported, plausible, certain defect; a wrong suggested fix lowers it). Findings below the minimum are dropped, the rest ordered by score, and the score shows on each finding. Setting: Admin → Model provider → Review → Self-check (Off, 3, 5 default, 7). A pass that fails or skips a finding fails the review. CodeReviewer keeps its System One check.

- **Large pull requests**: a diff over the budget (Review → Diff sent to the model, or a model's context) is no longer cut at a character count. Files are ranked (main language, other code, docs and config, lockfiles and generated output) and added whole, largest first; a file too big to fit shows its leading hunks up to half the budget; deleted files and hunks that only remove lines are listed instead of shown; every file left out is named with its line counts. Applies to language model reviews and hosted System One models; local System One models keep their change digest.

- **Dynamic context**: review diffs extend each code hunk upward to its enclosing declaration (function, method, class; JS/TS, Python, Go, Rust, Java/C#, Kotlin, Swift, Ruby, PHP), read from the head revision, and cut trailing context to one line. Hunks never repeat lines shown by the previous hunk, and a file whose content does not match the diff is left as git produced it. Setting: Admin → Model provider → Review → Context above a change (Off, 8, 16 default, 32 lines). Fast triage is unchanged.
